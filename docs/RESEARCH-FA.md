این سند خلاصه‌ی بررسی پروژه‌های مرجع است تا قبل از نوشتن کد، معماری درست انتخاب شود.

## ۱) پنل فعلی شما

`https://dee.up.railway.app/sub/...` بالاست و صفحه‌ی ساب فارسی با فهرست کانفیگ‌ها و فلگ دارد:

| فلگ | نام کانفیگ |
|---|---|
| 🇺🇸 | `𝙁𝙖𝙨𝙩-🇺🇸 2𝗫` و `🇺🇸 𝙐𝙣𝙞𝙩𝙚𝙙 𝙎𝙩𝙖𝙩𝙚𝙨` |
| 🇳🇱 | `𝙁𝙖𝙨𝙩-🇳🇱 2𝗫` و `🇳🇱 𝙉𝙚𝙩𝙝𝙚𝙧𝙡𝙖𝙣𝙙𝙨` |
| 🇩🇪 | `🇩🇪 𝙂𝙚𝙧𝙢𝙖𝙣𝙮` |
| 🇸🇬 | `🇸🇬 𝗦‌𝗜‌𝗡‌𝗚‌𝗔‌𝗣‌𝗢𝗥‌𝗘` |

نتیجه: «مولتی‌لوکیشن» فعلی ظاهراً فقط در سطح **نام/لیبل کانفیگ** است؛ اگر همه‌ی این ۸ کانفیگ به یک دامنه‌ی Railway وصل باشند، از نظر شبکه همه یک لوکیشن‌اند. تفاوت واقعی وقتی ایجاد می‌شود که هر لوکیشن یک **خروجی/آی‌پی متفاوت** داشته باشد.

## ۲) محدودیت‌های Railway که کل معماری را تعیین می‌کنند

| موضوع | واقعیت |
|---|---|
| پورت عمومی | هر سرویس فقط **یک** دامنه و **یک** پورت داخلی (`$PORT`) می‌گیرد → پنل + ساب + اینباند باید روی یک پورت جمع شوند (ترفند nginx). |
| منطقه (Region) | انتخاب ریجن **به‌ازای هر سرویس** است، نه پروژه → هر لوکیشن = یک سرویس جدا. |
| شبکه‌ی خصوصی | بین سرویس‌های یک پروژه/محیط کار می‌کند (حتی بین ریجن‌ها) اما **region-aware نیست** و فقط **IPv6** است → سرویس‌ها باید روی `::` گوش بدهند. |
| TCP Proxy | برای هر پورت دلخواه قابل فعال‌سازی است (برای gRPC/نود کاربرد دارد). |
| Volume | برای ماندگاری داده حیاتی است؛ یک Volume به یک سرویس وصل می‌شود و آن سرویس را به یک ریجن می‌چسباند. |
| بدون Docker محلی | همه‌ی تست‌ها باید با شبیه‌سازی محلی (uvicorn) انجام شود، بیلد واقعی روی Railway. |

## ۳) پروژه‌های مرجع که بررسی شد

### x4gpanell (همه wrapper ریلیوی، روش «build-time clone»)

| ریپو | نقش | نکته‌ی کلیدی |
|---|---|---|
| `3x-ui` | 3x-ui v3.8.5 + nginx | پنل روی `/managepanel/`، ساب روی `/sub/`، اینباند WS روی `/` — همه روی یک پورت |
| `Heimdall` | فورک بهینه‌ی 3x-ui | همان ترفند + صفحه‌ی ساب اختصاصی و تشخیص User-Agent کلاینت |
| `marzban` | پنل Marzban | سورس در زمان build کلون می‌شود (`MARZBAN_REF`)، ادمین با `SUDO_USERNAME` ساخته می‌شود |
| `marzban-node` | نود Marzban | `SERVICE_TLS=false` چون TLS را Railway ترمینیت می‌کند؛ گواهی کلاینت از متغیرها روی دیسک نوشته می‌شود |
| `PasarGuard-Node` | نود PasarGuard | ساخت خودکار گواهی با `CN = RAILWAY_PRIVATE_DOMAIN` + تولید `API_KEY` |
| `SuperJinX` | PasarGuard + Xray + nginx در یک سرویس | Volume روی `/var/lib/pasarguard`، پورت ۸۰۸۰، خودترمیمی، صفحه‌ی ساب |
| `NewYork` | Gateway مستقل | مدیریت لینک با سقف حجم/سرعت/IP، گروه ساب، ربات تلگرام |

### Vodiwalker (مولتی‌لوکیشن واقعی، آپدیت ۲۰۲۶-۱۰-۰۱)

معماری در `nodes.py`:

1. هر پنل می‌تواند «نود» شود → یک **توکن** (`vwn_...`) می‌سازد.
2. پنل اصلی، نود را با `url + token` ثبت می‌کند و هر ۳۰ ثانیه `/api/node/info` را می‌زند.
3. کل UI پنل اصلی می‌تواند با مسیر `/api/nodes/{id}/fwd/...` روی نود **ریموت اجرا** شود (فقط مسیرهای allowlist؛ بدون دسترسی به ادمین/رمز/بوت).
4. یک **گروه ساب** می‌تواند اینباندهای چند نود را با هم جمع کند → یک لینک ساب، چند لوکیشن.
5. `vodiwalker-worker` یک Cloudflare Worker است (VLESS روی WS + پورت‌های TLS + Proxy IP) برای عبور از محدودیت.

نتیجه‌گیری کلیدی: «مولتی‌لوکیشن» = **پنل مرکزی (کنترل‌پلین) + چند نود مستقل که هرکدام دامنه و آی‌پی خودش را دارد** + یک لینک ساب که همه را جمع می‌کند.

## ۴) سه معماری قابل اجرا روی Railway

### معماری A — پنل اختصاصی از صفر (کنترل کامل)
```
پنل مرکزی (FastAPI + UI فارسی + ربات)  ←── توکن ──  نود ۱ (ریجن EU)
        │  (یک لینک ساب برای مشتری)     ←── توکن ──  نود ۲ (ریجن US)
        └── SQLite روی Volume                            نود ۳ (ریجن SG)
```
* مزیت: همه‌چیز مال خودت، UI دقیقاً مطابق سلیقه، بدون وابستگی به upstream.
* معایب: کد زیاد (پنل + نود + ساب + ربات)، نیاز به تست.

### معماری B — Marzban + Marzban-node (استفاده از پنل آماده)
* پنل Marzban آماده است؛ فقط wrapper ریلیوی + راهنمای اتصال نودها لازم است.
* نودها با `SERVICE_TLS=false` از طریق دامنه‌ی عمومی/شبکه‌ی خصوصی وصل می‌شوند.
* مزیت: سریع، پایدار، داشبورد آماده. عیب: UI انگلیسی/کم‌سلیقه، تخصیص سرور به لوکیشن دستی است.

### معماری C — هر لوکیشن مستقل + سرویس جمع‌کننده‌ی ساب (مقاوم‌ترین)
```
Railway EU  :  3x-ui تک‌پورت (پنل + ساب + VLESS/WS)
Railway US  :  3x-ui تک‌پورت
Railway SG  :  3x-ui تک‌پورت
        └── Aggregator: یک سرویس کوچک که ساب همه‌ی لوکیشن‌ها را
            می‌خواند و یک لینک ساب واحد با فلگ‌ها به مشتری می‌دهد
```
* مزیت: هیچ سرویسی به سرویس دیگر وابسته نیست (یکی بخوابد، بقیه کار می‌کنند)، کمترین کد، سازگار با ابزارهای موجود.
* عیب: مدیریت کاربر در چند پنل پخش می‌شود (aggregator می‌تواند یکسان‌سازی کند).

## ۵) نکات فنی که حتماً باید رعایت شود

- [ ] یک پورت واحد: nginx جلوی همه‌چیز (پنل / ساب / اینباند / healthz).
- [ ] Volume روی مسیر داده (`/data`) وگرنه با هر دیپلوی همه‌چیز پاک می‌شود.
- [ ] `HOST=::` برای دریافت ترافیک شبکه‌ی خصوصی Railway (فقط IPv6).
- [ ] `PUBLIC_BASE_URL` از `RAILWAY_PUBLIC_DOMAIN` خوانده شود، نه `localhost`.
- [ ] توکن نود فقط روی مسیرهای allowlist؛ بدون دسترسی به ادمین/رمز/تنظیمات.
- [ ] محدودسازی brute-force روی توکن نود (rate limit + قفل موقت).
- [ ] برای لوکیشن‌هایی که آی‌پی Railway بسته است: Cloudflare Worker + Proxy IP.
- [ ] صفحه‌ی ساب باید هم `text/plain` (کلاینت) و هم HTML (مرورگر) بدهد → تشخیص با User-Agent.
